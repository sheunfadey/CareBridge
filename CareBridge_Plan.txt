## 1. YOUR ROLE AND MISSION

Act as a senior full-stack software architect, UI/UX designer, brand designer, database engineer, security engineer, DevOps engineer, QA engineer and product manager.

Build a complete, production-oriented, responsive, multi-tenant SaaS application named **CareBridge**.

**Working tagline:** Learn to Care. Grow Your Career. Make a Difference.

This is not a static website, design-only exercise, or dashboard demo. Build a functioning application with a real database, authentication, role-based permissions, data validation, file uploads, payment integration, transactional workflows, administrative approvals, audit trails, error handling, automated tests and deployment documentation.

The platform will initially target Nigeria and must accommodate Nigerian users, businesses, payment practices, currencies, mobile devices and network conditions.

The application combines:

1. Caregiver training and learning management.
2. Practical assessment and internship placement.
3. Caregiver recruitment and employment matching.
4. Care-home and home-care agency operations management.
5. Referral tracking and commission management.
6. Training payments and approved referral payouts.
7. Charity campaigns, scholarships and donor management.
8. Multi-tenant institutional administration.
9. Platform-wide super administration.
10. Reporting, analytics, notifications and audit logging.

Build the complete system through clearly defined implementation phases. Do not try to create every feature in a single unverified code-generation pass.

First inspect the existing project, preserve any working code, identify the current framework and produce an implementation plan. Then build, test and verify each phase before continuing.

Do not stop after producing a plan. Begin implementation immediately.

## 2. PRODUCT VISION

CareBridge connects the entire caregiver development journey:

Discover training → enrol → learn → complete assessments → demonstrate practical competence → undertake supervised internship → obtain verified credentials where applicable → apply for jobs → gain employment → continue professional development.

The platform also allows verified care homes and home-care agencies to manage staff, shifts, residents, approved care plans, daily records, incidents, inventory, invoices and operational reports.

Referral partners can introduce students or institutional customers and earn approved commissions under transparent programme rules.

Charities, NGOs, churches, companies and individual donors can sponsor training and monitor approved campaign outcomes.

### Product principles

- Safety before growth.
- Real functionality before decorative features.
- Mobile-first design.
- Clear and transparent financial records.
- Strict separation between organisations.
- Privacy by default.
- Verifiable training and employment records.
- Accessible design.
- Reliable performance on Nigerian mobile networks.
- No fabricated analytics or fake transactions.
- No false promises of employment or professional certification.
- No hidden deductions or silently changed financial terms.

- A maintained rich-text editor for lesson content where necessary.
- A secure background-job mechanism for scheduled notifications and processing.
- Paystack for eligible payment and transfer workflows, behind a provider abstraction.
- An email delivery provider abstraction.
- An SMS or messaging provider abstraction for later configuration.

Use current stable, mutually compatible package versions at implementation time.

Verify current package APIs before implementing integrations. Do not copy obsolete examples blindly.

If the repository already uses a compatible framework or contains working infrastructure, preserve it unless there is a documented reason to migrate.

### Architectural rules

1. Use Server Components by default where suitable.
2. Use Client Components only when browser interaction requires them.
3. Keep secrets on the server.
4. Do not expose service-role keys to the browser.
5. Keep privileged administrative operations in protected server-side services.
6. Validate all incoming data with schemas.
7. Enforce authorisation on the server, not only in the UI.
8. Use database transactions for multi-step financial operations.
9. Use idempotency for payment and payout processing.
10. Use background jobs for reliable scheduled work.
11. Store timestamps in UTC and display them in the user's configured timezone.
12. Default the platform to Africa/Lagos for Nigerian organisations.
13. Use NGN as the initial platform currency.
14. Store monetary amounts as integer minor units or a suitable exact decimal representation. Never use floating-point arithmetic for money.
15. Use explicit database constraints and indexes.
16. Maintain migration files for every schema change.
17. Separate development, testing and production environments.
18. Avoid circular imports, duplicated business logic and oversized components.
19. Keep UI, business services, data access and integration adapters separate.
20. Make error states actionable and understandable.

## 6. MULTI-TENANCY AND ORGANISATION MODEL

CareBridge must support both a central platform and independent organisations.

Supported organisation types:

- CareBridge-operated academy.
- Independent training provider.
- Care home.
- Home-care agency.
- Recruitment partner.
- Charity or NGO.
- Corporate training customer.

Each organisation must have:
- Unique ID.
- Display name.
- Organisation type.
- Verification status.
- Logo.
- Contact information.
- Address and service locations where appropriate.
- Subscription or contract information where applicable.
- Created date.
- Status.
- Permitted modules.
- Organisation-specific settings.

### Tenant isolation

Every tenant-owned record must include a tenant or organisation scope where appropriate.

Implement database-level RLS policies for all tenant-owned tables.

A user belonging to one organisation must not be able to read, modify or delete another organisation's private records merely by changing an ID in a URL or request.

Where a record is shared across organisations, define the sharing relationship explicitly.

Use least-privilege access.

Do not implement broad policies such as “any authenticated user can read everything.”

Create automated cross-tenant isolation tests.

The Super Administrator may perform authorised platform-wide operations through controlled server-side procedures, with audit logging.

Never rely solely on hidden menu items or frontend route guards for security.

### Financial correctness

Every commission record must reference:
- Referral partner.
- Attributed customer.
- Qualifying transaction.
- Applicable commission policy.
- Calculation basis.
- Gross eligible amount.
- Commission amount.
- Currency.
- Status.
- Eligibility date.
- Reversal information.
- Payout reference where applicable.

Use an immutable transaction ledger.

Never overwrite a paid commission to hide a reversal. Record an adjustment or reversal transaction linked to the original.

Commission status lifecycle:

`pending → eligible → approved → processing → paid`

Also support:
- `rejected`
- `reversed`
- `failed`
- `on_hold`

The exact allowed transitions must be validated server-side.

A refunded or disputed purchase must be handled according to the published commission policy.

Prevent self-referrals where prohibited, duplicate attribution and unauthorised changes to referral ownership.

## 16. PAYMENTS AND PAYSTACK INTEGRATION

Paystack is the initial preferred payment provider, subject to account eligibility, supported product availability and the current provider terms.

Keep the integration isolated so another compliant provider can be added later.

### Customer payments

- Training fees.
- Course purchases.
- Eligible subscriptions.

- Customer or payer.
- Product or purpose.
- Amount.
- Currency.
- Provider reference.
- Status.
- Created date.
- Verification timestamp.
- Webhook history.
- Refund state.
- Reconciliation status.

### Payment lifecycle

`initiated → pending → successful`

Also support:
- `failed`
- `cancelled`
- `refunded`
- `partially_refunded` where supported.

Verify payment status on the server using the provider's supported verification process.

Validate webhook signatures according to current provider documentation.

Make webhook processing idempotent.

Do not trust the browser redirect as proof of payment.

Do not credit a purchase twice if the same webhook is received more than once.

Never mark a payment successful before reliable verification.

### Referral payouts

Treat outgoing referral payouts as a separate workflow from incoming customer payments.

Implement:
- Payout request.
- Beneficiary details management.
- Appropriate identity and beneficiary checks.
- Eligibility calculation.
- Administrator review.
- Approval or rejection reason.
- Provider transfer request.
- Transfer status.
- Provider reference.
- Failed transfer handling.
- Reconciliation.
- Audit logging.

Require explicit authorisation for each financial operation.

Use idempotency keys where supported.

Do not retry transfers blindly after an ambiguous network timeout. First check the provider's transfer status to avoid duplicate payments.

Keep provider credentials on the server.

Do not store raw card details.

Use the current official Paystack API documentation and sandbox environment.

Before enabling live transfers, confirm that the platform's business model, Paystack account, beneficiary arrangement and intended use case are supported.

If the live payout arrangement is not yet approved, build the complete payout workflow in a disabled or sandbox mode and provide a clear configuration status. Never simulate a real successful transfer.

### Reconciliation

Build an administrative reconciliation page showing:
- Internal transaction.
- Provider reference.
- Expected amount.
- Confirmed amount.
- Transaction status.
- Difference.
- Last verification.
- Reconciliation result.

Flag mismatches for review.
